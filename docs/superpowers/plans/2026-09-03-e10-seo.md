# E10 · SEO e páginas públicas — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development.

**Goal:** The public content surface. Pages that answer "what is this line on my
bill", a page per issuer, a sitemap, an OG image per page, and valid rich
results — built from the only research this project actually has
(`CLAUDE.md` §7), and never claiming more than §7.0 says that research proves.

**Architecture:** Content is authored as a typed structure in `packages/core`
(`SeoPageContent`), serialised to markdown into `seo_pages.body_md` by a seed in
`packages/db`, and read back by the route from `seo_pages` — RF-280's
"conteúdo vindo de `seo_pages`" is literal. The parser and the serialiser live
beside each other in `packages/core` so the round trip is one testable unit.
Every page is a server component with zero client JS.

## Global Constraints

- **`INV-001`** — the product takes no percentage of anything recovered. No page
  may say or imply otherwise; the landing page's existing footnote ("não recebe
  percentual de nada que você recuperar") is the wording to echo.
- **`INV-002`** — never handle anyone's credential. "Como conferir" steps send the
  person to the company's own app/site or to the printed bill. Never "entre com
  seu login", never a form, never a deep link that asks for a password.
- **`INV-004` / `INV-005`** — §14.3's vocabulary via `lintUserFacingText` on
  **every** user-facing string, including OG-image strings and metadata
  descriptions. No promise of an outcome, ever.
- **No company is named as having done something wrong.** A page about a charge
  type is not a page accusing an issuer — and not a page accusing the service
  company either (Skeelo, Ubook, Editora Abril, Chubb are real companies). This
  is enforced by a new invariant spec, not by good intentions.
- **§7.0's ceiling.** The lexicon was built from complaint text with no real
  invoice in hand. Only ✅ **confirmed** entries become pages; ⚠️ and ❔ entries
  do not. Every page carries a provenance paragraph saying where this came from.
- **RF-281** — an aggregate number renders only at `invoicesSeen ≥ 50`. Today
  `aggregates` is empty, so nothing renders. That is the correct output, and the
  test proves both sides of the threshold.
- **RNF-03/04/05/09** — LCP ≤ 2,0 s, CLS ≤ 0,05, initial JS ≤ 120 kB gzip, axe
  clean in both themes. New pages are server-rendered with no client component.
- **§13.1** — tokens only, no invented colour. Fraunces display, IBM Plex Mono
  for labels and every number, `--mark` for the hand-drawn underline, `--deep`
  as the one dark surface. Read `home.module.css`, `laudo.module.css`,
  `caso.module.css` before writing CSS. Speak the existing language.
- ESM with `verbatimModuleSyntax` (`.js` on relative imports, `import type`).
  English code and commits; user-facing strings pt-BR. Money is integer cents.
- **Every new assertion watched failing before it is trusted.**

**What already exists:** `seo_pages` (`issuer_id` NOT NULL, `charge_slug`,
`title`, `body_md`, `status draft|published`, unique on `(issuer, charge)`);
`aggregates` with `invoicesSeen`/`flagged`/`resolved`; `cases` with `outcome`;
`issuers` with `slug`/`displayName`/`sections`/`playbook`;
`TELECOM_PLAYBOOK_V1`; `lintUserFacingText`; `ImageResponse` used for real in
`app/api/card/[token]/route.tsx`; `lighthouserc.cjs` and `scripts/check-a11y.mjs`
with their "this route is not covered yet" warning machinery.

**Known gap this plan does not close (report it, do not paper over it):**
`seo_pages.issuer_id` is NOT NULL and only six telecom issuers are seeded, so
§7.2 (processor descriptor prefixes) and §7.3 (embedded card insurance) — the
highest-confidence material in the whole lexicon — have nowhere to be published.
§18's "30 páginas" is a delivery-size number with no RF behind it; the confirmed
research supports ~19 charge pages plus 6 issuer pages. Ship what is confirmed.

### Task 1: The content model — types, markdown round trip

**Files:** `packages/core/src/seo/content.ts`, `packages/core/src/seo/content.test.ts`, export from `packages/core/src/index.ts`.

The page content structure, its markdown serialisation, and the parser that
reads it back. Pure, no I/O. `packages/core`'s coverage floor is 90% on all four
metrics.

```ts
export type SeoFaqEntry = { question: string; answer: string };
export type SeoSection = { heading: string; paragraphs: string[] };
export type SeoPageContent = {
  intro: string;                 // one paragraph, no heading
  sections: SeoSection[];        // rendered as h2 + paragraphs
  faq: SeoFaqEntry[];            // rendered under a fixed h2, each as h3 + paragraph
  provenance: string;            // the §7.0 disclosure paragraph, last block
};
export function serializeSeoContent(content: SeoPageContent): string;
export function parseSeoContent(markdown: string): SeoPageContent;
```

The markdown subset is **exactly** what `serializeSeoContent` emits and nothing
else: `## ` headings, `### ` headings, and blank-line-separated paragraphs. No
lists, no inline emphasis, no links, no raw HTML. Keep it that narrow on purpose
— the renderer in Task 3 has to be able to turn it into React elements without a
markdown library (RNF-05) and without ever interpreting a string as HTML.

The FAQ section is delimited by a fixed exported heading constant
(`SEO_FAQ_HEADING = "Perguntas frequentes"`) and the provenance block by another
(`SEO_PROVENANCE_HEADING`). `parseSeoContent` must reject — throw, with a message
naming the offending line — anything it cannot round-trip: an unknown block type,
a `###` outside the FAQ section, a heading with no body.

**The test that matters is the round trip**: for a table of contents fixtures
(including one with an empty FAQ, one with multiple paragraphs per section, and
one whose text contains a `#` character mid-sentence),
`parseSeoContent(serializeSeoContent(c))` deep-equals `c`. Watch it fail first.

Also export `seoChargeSlug`/validation for the slug shape used in URLs
(lowercase, `a-z0-9-`, no leading/trailing dash) — the route and the seed must
agree on one definition, and a slug that differs between them is a 404.

### Task 2: The corpus and the seed — and the invariant that no company is accused

**Files:** `packages/db/src/seeds/seo-pages.ts` (+ a `.content.ts` sibling if the
corpus is long enough to want its own file), `packages/db/src/seeds/index.ts`,
`packages/db/test/seeds-seo.test.ts`, `packages/db/test/invariants/seo-content.spec.ts`.

Write the pages. This is the substance of the block, and it is a writing task as
much as a coding one. **Read `CLAUDE.md` §7 in full first, §7.0 before anything
else.**

**What gets a page.** Only ✅ **confirmed** entries, paired with the issuer the
research actually observed them at:

- §7.1.2's confirmed SVA items → `vivo-movel` (Skeelo, GoRead, Hube Jornais,
  NBA Básico, Clube de Revistas, FunKids, TDATA, McAfee, Vivo Meditação Lite),
  plus §7.1.1's "Serviços Digitais III"; Ubook → `claro-movel` **and**
  `tim-movel` (the research confirms both, under different branding).
- One "what is an SVA section" page per seeded issuer whose section names §20.1
  seeds and §7.1.1 corroborates: `claro-movel`, `vivo-movel`, `tim-movel`, `oi`,
  `sky`, `algar`.
- Vivo's "Cobrança de Serviços de Terceiros" section, which §7.1.1 confirms
  separately from the generic SVA anchor.

⚠️ single-source and ❔ needs-a-real-invoice entries get **no page**. §7.2 and
§7.3 get no page at all — there is no card issuer row to hang them on (see the
gap note above); say so in the seed's doc comment rather than inventing an
issuer.

**What each page says**, in this order:

1. **What this line is.** The service, plainly. Where the research says the
   product is a real, legitimately sold subscription with documented opt-in
   (Ubook's published Claro authorisation contract, McAfee's own Vivo activation
   page), the page **says so**. Leaving that out to make the page punchier would
   be the dishonest version.
2. **Why it can appear on a bill.** How third-party/value-added billing works,
   described as a mechanism, not as a scheme.
3. **How to check whether you agreed to it.** Concrete steps against the printed
   bill and the company's own channels. `INV-002`: never a credential, never a
   form here.
4. **What the rules say.** Norms only, from data that already exists in this
   repo (`TELECOM_PLAYBOOK_V1`'s `legalRefs` — Anatel Res. 765/2023, CDC art. 42,
   Decreto 11.034/2022). Cite the norm; do not apply it to a company.
5. **Perguntas frequentes** — 2 to 4 entries, real questions a person with this
   line on their bill would ask. This is what becomes the JSON-LD `FAQPage`.
6. **Provenance** — one shared constant, on every page, saying in pt-BR what
   §7.0 says: this description was assembled from public complaint reports and
   the companies' own published pages, not from reading real invoices; a charge
   appearing here is not a statement that any company did anything wrong; the
   only way to know whether *your* charge is right is to check whether you
   agreed to it.

**Copy discipline.** §14.2's pairs, verbatim in spirit: "para você verificar",
never "cobrança ilegal"; "a norma prevê", never "você tem direito a receber".
Nothing promises an outcome. Titles are plain: `"Skeelo na conta da Vivo: o que
é essa linha"`, not `"Vivo está cobrando Skeelo sem autorização"`.

**The seed** upserts by `(issuerId, chargeSlug)` like `issuers.ts` and
`lexicon.ts` do, resolving `issuerId` by slug at seed time (fail loudly if the
issuer row is missing — a silently skipped page is a silently missing page), sets
`status: "published"`, and writes `serializeSeoContent(content)` into `bodyMd`.
Wire it into `seedAll` **after** `seedIssuers`.

**Two test files, both new assertions to watch fail:**

- `packages/db/test/seeds-seo.test.ts` — seeding is idempotent; every row's
  `bodyMd` parses back to the authored content; every `chargeSlug` is valid and
  unique per issuer; every issuer slug referenced exists.
- `packages/db/test/invariants/seo-content.spec.ts` — the honesty gate:
  1. `lintUserFacingText` returns `ok` for every title, every paragraph, every
     question and every answer, with **no** citation ranges granted (nothing here
     is a verbatim quotation of a norm, so nothing earns the §14.3 exemption).
  2. **No accusation.** Build the set of company names in play — every issuer
     `displayName` and alias from the issuers seed, plus every product/company
     name the corpus itself names (Skeelo, Ubook, GoRead, McAfee, TDATA,
     Editora Abril, …) — and assert that no occurrence of any of them sits within
     the same sentence as any term from an accusatory lexicon
     (`cobrou sem`, `fraude`, `fraudou`, `golpe`, `enganou`, `lesou`, `abusiva`,
     `abusivo`, `irregular`, `má-fé`, `descumpriu`, `sem autorização`,
     `sem consentimento`, `escondido`, `esconde`). Sentence-scoped, not
     whole-document, or the assertion means nothing on a long page.
  3. No page's text contains an SVA/insurance/prefix term the lexicon marked
     ⚠️ or ❔ — the corpus may not quietly widen past what §7 confirmed.

  Write each of these three so you have watched it fail on a deliberately bad
  fixture string before you trust the corpus passing it.

### Task 3: `/cobranca/[issuer]/[charge]` (RF-280, RF-281)

**Files:** `apps/web/app/cobranca/[issuer]/[charge]/page.tsx`, `data.ts`,
`markdown.tsx` (the block renderer), `cobranca.module.css`, tests under
`apps/web/test/cobranca/`.

RF-280: static with daily revalidation, content from `seo_pages`.

- `export const revalidate = 86400;`
- `generateStaticParams()` reads every `status = 'published'` row and returns
  `{ issuer, charge }` for each. **It must not break a build with no database**:
  wrap the read, and on failure log a loud, specific warning (naming
  `DATABASE_URL` and what is consequently not prerendered) and return `[]`.
  `next build` sets `NODE_ENV=production`, and `getUnscopedDb()` throws when
  `DATABASE_URL` is unset in production — without this, `pnpm build` stops
  working for every developer who has no Postgres. Test both branches.
- The loader joins `seo_pages` to `issuers` by slug, requires
  `status = 'published'`, and `notFound()`s otherwise (draft rows are not
  reachable by URL — assert it).
- The renderer turns Task 1's parsed blocks into React elements. No markdown
  library, no `dangerouslySetInnerHTML`, ever — headings and paragraphs only.
- **RF-281's aggregate block.** Sum `aggregates.invoicesSeen` for this issuer and
  this charge's normalised description over the published window; below 50 the
  block does not render at all — not "0", not "dados insuficientes" with an empty
  figure, nothing. At or above 50 it renders the count and the flagged share, in
  mono with `tabular-nums`. Test 49 → absent, 50 → present.
- `generateMetadata`: title, description (derived from the intro, truncated on a
  word boundary), `alternates.canonical`, `openGraph` (Next fills the image from
  Task 6's `opengraph-image.tsx` — do not hand-roll an `og:image` tag).
- **JSON-LD `FAQPage`** in a `<script type="application/ld+json">`, only when the
  page has FAQ entries, serialised with `JSON.stringify` (never string
  concatenation) and escaped so a `<` in the content cannot close the tag. Test
  the emitted JSON parses and has `@context`, `@type: "FAQPage"`, and one
  `Question`/`acceptedAnswer` pair per entry, in order.
- Design: §13.1's language as the existing screens speak it — mono uppercase
  eyebrow, Fraunces headline, the `--mark` hand-drawn underline used **once**,
  hairline `--line` rules between sections, `--deep` reserved for the one
  confidence surface (here: the provenance block, which is exactly a "seção de
  confiança"). Zero client JS.

### Task 4: `/empresa/[issuer]` (RF-282)

**Files:** `apps/web/app/empresa/[issuer]/page.tsx`, `data.ts`,
`empresa.module.css`, tests under `apps/web/test/empresa/`.

RF-282: most-flagged charges, observed resolution rate, and the playbook's
deadlines. Acceptance: the numbers match `aggregates` and `cases`.

Three blocks, each with its own honest floor:

1. **Cobranças mais sinalizadas** — from `aggregates`, ordered by `flagged`,
   subject to RF-281's ≥ 50 `invoicesSeen` gate **per row**. A row below the
   threshold is not shown at all. Links to the `/cobranca/...` page when one
   exists for that charge.
2. **Taxa de resolução observada** — from `cases` (`outcome = 'resolved'` over
   closed cases for this issuer). The PRD sets no floor for this one; apply the
   same 50 and say in the code comment that it is RF-281's number borrowed
   deliberately, because a rate computed from three cases is noise presented as
   fact. Below the floor the block does not render.
3. **Prazos do playbook** — from `issuers.playbook`, always available. Stage,
   channel, response window, and whether the window is in business days. This is
   configuration, not a claim about the company, and it is what the page can
   honestly carry today.

Because blocks 1 and 2 render nothing until real invoices exist, the page's
**written empty state is the deliverable** (§13.3: "toda tela tem estado vazio
escrito, nunca em branco"). Say plainly that there are not yet enough invoices
from this company to publish numbers, without implying the numbers would be
damning when they arrive.

`generateStaticParams` from `issuers` (same no-database tolerance as Task 3),
`revalidate = 86400`, `generateMetadata`, and a `notFound()` for an unknown slug.
Same design language, zero client JS.

### Task 5: `sitemap.xml`, `robots.txt`, and keeping private pages out of both

**Files:** `apps/web/app/sitemap.ts`, `apps/web/app/robots.ts`,
`apps/web/lib/site.ts`, `noindex` metadata on `/laudo/[id]`, `/l/[token]`,
`/caso/[id]`, tests.

RF-280's acceptance is explicit: **`sitemap.xml` includes all of them.**

- `sitemap.ts` lists `/`, every published `/cobranca/[issuer]/[charge]`, and
  every `/empresa/[issuer]`, with `lastModified` from each row's `updatedAt`.
  Same no-database tolerance, and the same loud warning.
- The absolute base URL comes from `APP_BASE_URL`. `lib/container.ts` already has
  `resolveAppBaseUrl` with exactly the right posture (refuses to guess in
  production, dev fallback) — export it and reuse it rather than writing a second
  one that can drift.
- `robots.ts`: allow the public surface; `disallow` `/api/`, `/laudo/`, `/l/`,
  `/caso/` and `/admin`; point at the sitemap. `/l/[token]` is someone's real
  bill behind a capability token — it must never be indexed.
- Add `robots: { index: false, follow: false }` metadata to the three private
  route trees. Belt and braces: `robots.txt` asks politely, page metadata is what
  actually keeps a leaked URL out of an index.
- Test: the sitemap contains every published row and **no** draft row; a draft row
  added to the fixture does not appear; the three private prefixes are disallowed.

### Task 6: OG image per page (RF-283)

**Files:** `apps/web/app/cobranca/[issuer]/[charge]/opengraph-image.tsx`,
`apps/web/app/empresa/[issuer]/opengraph-image.tsx`, a shared builder under
`apps/web/lib/og/`, tests.

`app/api/card/[token]/route.tsx` is the reference for how this repo builds an
`ImageResponse`: `React.createElement` rather than JSX so the tree's shape is
readable and assertable, `TOKENS.light` from `@pentefino/ui` (a shared PNG has no
viewer theme), 1200×630, and a copy object built by a named function so a test can
lint every string the image can ever render.

Do the same here. Extract the shared frame (background, brand mark, padding,
sizes) into one builder both routes call; do **not** import from the card route
or refactor it — it has its own token-and-revocation constraints that have
nothing to do with these pages.

Cache headers: unlike the card, these images are derived from published editorial
content with no capability token to revoke, so the card's deliberate 5-minute
cap does not apply. Say that in a comment rather than copying the header blindly.

Tests: the copy passes `lintUserFacingText`; the tree carries the expected
strings; an unknown issuer/charge produces the not-found path rather than an
image full of `undefined`.

### Task 7: Make the gates measure these pages

**Files:** `scripts/check-rich-results.mjs` + its `node --test` sibling,
`scripts/db-setup.mjs` + sibling, `apps/web/lighthouserc.cjs`,
`scripts/check-a11y.mjs`, `.github/workflows/ci.yml`, `package.json`.

§18's gate for this block is **"Rich results válidos"**. Nothing in this repo
checks that yet, so build the check.

**`scripts/check-rich-results.mjs`** — same shape as `check-a11y.mjs` and
`check-bundle-budget.mjs` (exported pure functions, a thin CLI, never a silent
vacuous pass). Given a base URL it:
1. fetches `/sitemap.xml`, parses out every URL, and **fails if there are none** —
   an empty sitemap is a broken gate, not a clean one;
2. fetches each page and asserts HTTP 200 (a 404 measured as "valid" is the exact
   trap `lighthouserc.cjs`'s header warns about);
3. asserts `<title>`, a meta description, `og:title`, `og:description`,
   `og:image` and a canonical link are present and non-empty;
4. parses every `application/ld+json` block: it must be valid JSON, have
   `@context` `https://schema.org`, and where `@type` is `FAQPage`, have a
   non-empty `mainEntity` where every item is a `Question` with a
   `name` and an `acceptedAnswer.text`;
5. fetches the `og:image` URL and asserts 200 with an image content type.

**`scripts/db-setup.mjs`** — applies migrations and runs `seedAll` against
`DATABASE_URL`. Refuses, loudly, when `DATABASE_URL` is unset. This is what gives
CI a database with published `seo_pages` rows, which is what makes every gate
below measure a real page instead of an empty route tree.

**CI wiring** (`.github/workflows/ci.yml`):
- Add a `postgres:16` service to the `verify` job with a `pg_isready` health
  check. Migration 0000 starts with `CREATE EXTENSION IF NOT EXISTS pg_trgm`,
  which the official image carries.
- Add a "Set up database" step running `scripts/db-setup.mjs`, **after** the test
  steps, with `DATABASE_URL` in its own step env.
- Give `DATABASE_URL` to the build steps, the Lighthouse step and the
  start-the-app step — **step-scoped, not job-scoped**. The unit/contract tests
  above build their own PGlite databases and must keep doing so; a job-wide
  `DATABASE_URL` would silently repoint `getUnscopedDb()` underneath them.
- Add the rich-results check as its own step, against the already-running server.

**`lighthouserc.cjs`** — add one `/cobranca/...` URL and one `/empresa/...` URL
to `urls` (RNF-03/RNF-04 name "as páginas SEO" explicitly, so this is the config's
whole reason to grow). Update the file-header comment: it currently explains at
length why only the landing page is measured, and that explanation is about to be
half-wrong. Extend the existing "route exists but is not covered" warning loop so
it still fires for `/laudo` and `/l`, which remain uncovered.

**`scripts/check-a11y.mjs`** — add the same two paths to `TARGET_PATHS`, and add a
**status assertion inside `scanUrl`**: axe on Next's 404 page passes trivially, so
a wrong URL or a missing seed would turn RNF-09 into a green check measuring
nothing. `page.goto` returns a response — assert it is 200 and throw with the URL
in the message otherwise. Watch that assertion fail (point it at a URL that does
not exist) before trusting it.

**`package.json`** — register the two new `node --test` files in the root `test`
script beside the existing five.

## Definition of done

- `pnpm lint`, `pnpm typecheck`, `pnpm test` green — exit codes read directly,
  never through `| tail`.
- `pnpm --filter @pentefino/web build` succeeds **with and without**
  `DATABASE_URL`.
- With a seeded database and the app running, `node scripts/check-rich-results.mjs`
  passes, and `node scripts/check-a11y.mjs` passes on the new pages in both themes.
- Every new assertion has been watched failing.
