# E5 · Escalada — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Count the legal deadlines for the person, tell them when one expires, and produce the next step's text with that expiry already stamped on it — so a case does not die of being forgotten.

**Architecture:** The transition table and the deadline arithmetic are pure and live in `packages/core`. The wait itself is a row in `cases.next_deadline_at`, scanned by a job — durable because the database is, not because a worker is. `TaskQueue` stays the port; Trigger.dev slots in later for replay without changing the shape.

## Global Constraints

- **`INV-002`** — the system never sends anything to a channel on the user's behalf, and never handles a third party's credential. It produces text and a deep link; the person clicks.
- **`INV-003`** — the user is the author of every document. `packages/ai/test/invariants/authorship.spec.ts` enforces it.
- **`INV-004` / `INV-005`** — §14.3's vocabulary, via `lintUserFacingText`, on every user-facing string.
- **`INV-008`** — user data through `withUser`. `cases.userId` is NOT NULL, so an anonymous session owns no case; `resolveSession` turns a claimed session id into a user id.
- **A3** — every state transition writes an `events` row. `case_created`, `protocol_entered`, `stage_advanced` and `deadline_expired` are already in the catalogue and have never been emitted by anything.
- Money is integer cents. Dates: `timestamptz` for instants, `date` for civil dates. ESM with `verbatimModuleSyntax`. English code and commits; user-facing strings pt-BR. Windows locally, Linux in CI.

**What already exists:** `nextStage`'s closed signature, throwing on every input, with `StageEvent`, `StageTransition` and `CaseOutcome`; `Playbook`/`Stage` types and §20.2's telecom playbook in the PRD; `cases` with `stage`, `stageEnteredAt`, `nextDeadlineAt`, `workflowRunId`, `protocolToken`, `outcome`, `recoveredCents`, `closedAt` and the partial index `cases_next_deadline`; `case_protocols` and `case_documents`; `assembleContest` and E4's generator; `withUser`'s `caseDocument`/`createCaseDocument`/`editCaseDocument`; the `TaskQueue` and `Mailer` ports with local adapters; `expire-files` as the shape a scheduled job takes here.

**The hole this block has to close first:** nothing creates a case. `cases` has been in the schema since E0, E4 built documents that hang off one, and there is no `createCase`, no `POST /api/cases`, and no `case_created` event ever written. Every other task here presumes a case exists.

### Task 1: The national holiday calendar and the deadline calculator

**Files:** `packages/core/src/cases/holidays.ts`, `packages/core/src/cases/deadline.ts`, tests.

RF-181: deadlines come from the issuer's playbook, in calendar days or business days, against the Brazilian national holiday calendar. **Its acceptance is exact: 10 business days started on a Thursday before a holiday must land on the correct date.** Work that example through by hand before writing code, and make it a test.

Brazil's moveable holidays derive from Easter — Carnaval is Easter minus 47 days, Sexta-feira Santa minus 2, Corpus Christi plus 60 — so this needs a computus, not a hardcoded list. The fixed ones are federal law and change by law: treat the calendar as versioned reference data with its source recorded, the way §12.3 treats ANEEL's tables, not as a constant nobody will revisit.

Decide and report: whether the day a deadline starts counts as day zero or day one, what happens when a calendar-day deadline lands on a holiday or a weekend, and which timezone the arithmetic happens in — a deadline computed in UTC for a person in Brazil can be a day off, and a day is the difference between a valid escalation and a premature one.

Pure, no I/O. `packages/core`'s coverage floor is 90% on all four metrics.

### Task 2: `nextStage` — the whole decision table, and a playbook that exists

**Files:** `packages/core/src/cases/next-stage.ts` and `next-stage.table.ts`, `packages/db/src/seeds/`, tests.

The last function in the core that still throws on every input. §9.1 gives the state machine and names `packages/core/cases/nextStage.table.ts`, **with a test covering every combination of `stage × event × category`**.

Read §9.1's diagram carefully — it carries branches that are easy to miss: `ombudsman` applies only to `card`; `procon` is optional; a case with no protocol for 30 days becomes `stalled`, which §9.1 calls a *sub-state* that returns to `sac`; and any stage, after 60 days without user action, closes as `abandoned`. Note that `stalled` is **not** in `STAGES` and the `cases_stage_values` CHECK constraint rejects it, which is consistent with it being a sub-state — decide how it is represented and say why.

`StageTransition` already carries `outcome` and `stampDeadline`. Use Task 1's calculator for `nextDeadlineAt`.

**Seed the telecom playbook.** `issuers.playbook` is `jsonb` and every seeded issuer has `null` there, so `nextStage` currently has no real playbook to be tested against and no deadline can be computed for any live issuer. §20.2 is the reference; seed it as versioned configuration (A5), the way the extraction prompt is seeded.

An unmapped combination must still throw rather than guess: a wrong stage silently loses someone's case. But after this task there should be no unmapped combination, and the test that enumerates them is what proves it.

### Task 3: The durable wait

**Files:** `apps/jobs/src/tasks/case-deadlines.ts`, additions to `withUser`, tests.

RF-180: each case runs a durable workflow, its state mirrored in `cases.stage`. **The acceptance is that restarting the service mid-wait does not lose the case — test it with a simulated deploy.**

The durability comes from the database, not from a worker. `cases.next_deadline_at` and the partial index `cases_next_deadline` have been in the schema since E0 waiting for exactly this: a job scans for deadlines that have passed, applies `nextStage`, stamps the expiry as a `deadline_expired` event and the move as `stage_advanced`, and schedules the next one.

Write the restart test so it means something: persist a wait, discard every in-memory structure the way a redeploy would, rebuild from the database alone, and assert the case advances correctly. A test that keeps the same process alive proves nothing about a restart.

**RF-186 is this job's other half:** 30 days with no protocol enters `stalled`; 30 further days with no action closes the case as `abandoned`, with an event. Simulate time rather than waiting for it — `expire-files` shows the injected-clock pattern this codebase uses.

`ADR-02` picked Trigger.dev for replay and long-running tasks, and that remains right — say plainly in the code what this arrangement does and does not give compared to it, so nobody reads a database scan as a full workflow engine.

### Task 4: A case can be created, read and closed

**Files:** `createCase`/`caseDetail`/`closeCase` in `packages/db/src/with-user.ts`, `apps/web/app/api/cases/route.ts`, `apps/web/app/api/cases/[id]/route.ts`, `apps/web/app/api/cases/[id]/close/route.ts`, tests.

§8.2's three missing case endpoints, and the `withUser` methods behind them.

- **`POST /api/cases`** → `201 { caseId }` from `{ invoiceId, findingIds[] }`. Writes `case_created`. The invoice and every finding must belong to the caller; a finding from someone else's invoice must not be smuggled in through the array. The first stage and its deadline come from the issuer's playbook via Task 2.
- **`GET /api/cases/:id`** → `{ case, documents[], protocols[], timeline[] }`. The timeline is the case's `events` rows, which is what makes A3 worth having.
- **`POST /api/cases/:id/close`** → `{ outcome, recoveredCents?, note? }`. `recoveredCents` feeds §1.4's north-star metric, so it is integer cents and the outcome is one of `CASE_OUTCOMES`.

`INV-008` applies throughout: `cases.userId` is NOT NULL, so use `resolveSession`; a wrong user and a nonexistent case must be indistinguishable, as the report route already does it.

### Task 5: Recording a protocol, and the document that cites it

**Files:** `apps/web/app/api/cases/[id]/protocol/route.ts`, `apps/web/app/api/cases/[id]/advance/route.ts`, `packages/ai` and `packages/core/src/documents/assemble.ts` additions, tests.

RF-184: posting a protocol releases the wait and schedules the next deadline, **and the workflow resumes in under 30 s**. It writes `protocol_entered` and a `case_protocols` row.

RF-182: when a case advances **because a deadline expired**, the generator receives `deadlinesExpired` and the resulting document names the channel, the protocol number and both dates. E4's `ContestPromptInput` deliberately has no such field — its agent left it out rather than invent a shape that would collide with this block. Define it here, and make the acceptance real: **assert the produced document contains the protocol number and both dates**, not merely that the field was passed.

The expiry is a fact read from `events`, not recomputed at generation time — that is why Task 3 writes `deadline_expired`.

### Task 6: The case screen, its deep links, and reminders that do not nag

**Files:** `apps/web/app/caso/[id]/`, `apps/jobs/src/tasks/case-reminders.ts`, tests.

**RF-183:** a deep link per channel, the document text copied to the clipboard, and the attachment checklist. **`INV-002`'s acceptance is that no data is sent to the channel by the system** — the button copies and opens, and that is all. Write the test that proves nothing leaves; a fetch to the channel's domain from this page is the failure being ruled out.

The playbook carries `deepLink` per stage (§20.2 has one for `consumidor_gov`); stages without one show the channel without a link rather than inventing a URL.

**RF-185:** reminders in layers, push then e-mail, **suppressed if the user opened the case in the last 24 hours**. The suppression is the requirement: a product that mails someone about a case they just looked at is a product they mute. The `Mailer` port and its local adapter exist; push is E12, so name that gap rather than faking it. "Opened the case" needs a recorded fact — decide what records it and say so.

The `laudo/[id]` page is the precedent for structure, CSS modules and the RNF-05 bundle budget. RNF-11's accessibility gate applies to any new page.

### Task 7: The dossier

**Files:** `apps/jobs/src/tasks/dossier.ts` or a route, tests.

RF-187: reaching `jec_ready` produces a chronological PDF carrying every document, protocol and date, plus the attachment list. The acceptance is that the PDF opens and contains the complete timeline.

This is what a person hands to a small-claims court, so what it omits matters as much as what it includes. `INV-007`'s masking applies to everything persisted — work out what a dossier meant for a judge needs that a shared card must not have, and say what you decided. Note that the invoice file itself may already be gone: RF-110's expiry deletes it after 30 days, and a case can outlive that.

Decide how the PDF is produced and justify it against RNF-05's bundle budget if anything lands in the client.
