# E3 · Laudo e card — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the product a face — the report a person actually reads, the progress they watch while it is computed, the card they share, and the public page that brings the next person in.

**Architecture:** Next.js App Router in `apps/web`, server components by default, client components only where interaction demands it. Styling from `packages/ui`'s §13.1 tokens; no shadcn default skin. The queue stops running inline so progress has something to report. Everything user-facing passes `packages/ai`'s forbidden-term lint.

**Tech Stack:** the existing stack. `ImageResponse` from `next/og` for the card. No component library beyond what §13.1's tokens support; if a task believes it needs one, it must justify it against RNF-05's 120 kB budget.

## Global Constraints

- **Language:** every user-facing string in pt-BR, and every one of them passes `lintUserFacingText` from `@pentefino/ai`. Code, identifiers, commits and comments in English.
- **§14.2's phrasing is mandatory**, not a suggestion: "para você verificar", never "cobrança ilegal"; "a norma prevê devolução em dobro", never "você tem direito a receber"; "não conseguimos ler essa fatura com segurança", never "erro ao processar arquivo".
- **§13.3's interface rules:** never a mute spinner — every wait shows a named step; confidence always visible beside a finding **in plain language, not a raw number**; the doubled amount beside the charged one when the legal basis allows; a destructive action confirmed by typing; every empty state written; visible focus on every interactive element; `prefers-reduced-motion` respected.
- **`INV-007`:** no PII leaves the server on a public surface. The card and `/l/[token]` are the two places this is newly at risk.
- **`INV-008`:** every read of user data goes through `withUser`. The public page is the deliberate exception and reaches its data by token, never by session.
- **RNF-05:** initial JS bundle ≤ 120 kB gzip. **RNF-03:** LCP ≤ 2,0 s. **RNF-09:** WCAG 2.1 AA, axe clean. **RNF-10:** light and dark, complete tokens.
- Money is integer cents. ESM with `verbatimModuleSyntax`. Windows locally, Linux in CI.

**What already exists:** the anonymous session (signed, 30 days); `GET /api/invoices/:id/report` returning findings, totals, issuer, the RF-124 band and `askUser`; `POST /api/findings/:id/feedback`; shadow findings already excluded from the report and its totals; `packages/ui`'s tokens and Tailwind preset; the local mailer behind its port.

### Task 1: The queue stops blocking the response

Nothing else in this block works until this does. `POST /api/invoices/:id/process` currently awaits the whole ingestion, so it returns only when the report is already finished — there is no progress to stream, and RNF-01's "time to report" is the request duration by definition.

**Files:** `packages/adapters/src/queue/in-process.ts`, `apps/web/app/api/invoices/[id]/process/route.ts`, tests.

Make the in-process queue run its handler outside the response cycle while keeping the `TaskQueue` port unchanged — Trigger.dev arrives in E5 and must not require a second rewrite. Keep every property the queue already has and has tests for: idempotency by key including concurrent duplicates, an unknown task failing loudly, and a throwing handler leaving its key free for a genuine retry.

Decide deliberately what `POST /process` now returns and when, and what happens to an error raised after the response was sent — today a failure surfaces as an HTTP status, and it no longer can. The invoice row and its `invoice_failed` event already record it; make sure nothing that used to be visible becomes silent.

---

### Task 2: Progress by SSE (RF-141)

**Files:** `apps/web/app/api/invoices/[id]/status/route.ts`, tests.

§8.2 specifies a stream of `{ status, step, progressPct }` over the steps `classifying | extracting | validating | analyzing | done | needs_review | failed`. RF-141's acceptance is **at least four distinct events between `queued` and `analyzed`**.

The events already exist — the ingest task writes one per transition, which is what A3 is for. Read them; do not invent a second progress mechanism that can disagree with the event trail.

Handle what a stream makes possible: a client that connects after the work already finished (it must still learn the outcome, not hang), a client that disconnects (the server must not leak the connection), and an invoice belonging to another session (`INV-008` applies to a stream exactly as to a request).

---

### Task 3: The report screen (RF-143)

**Files:** `apps/web/app/laudo/[id]/page.tsx` and its components, tests.

**Invoke the `frontend-design` skill before writing any of this.** §13.1 states the visual identity and says explicitly not to use shadcn's default skin, which reads as a generic AI app. The tokens exist in `packages/ui`.

The screen shows: the total to check, the doubled total where the legal basis allows it, the list of findings with **confidence in words**, one sentence of evidence each, and the "isso eu contratei" button — which records the feedback and removes the item from view.

§13.2 names the states this screen must have: with findings, without findings, `needs_review`, and with pending questions. Build all four; an empty state is written text, never a blank area.

The wording is not yours to choose — §14.2 gives it. Assert with `lintUserFacingText` in a test that every string this screen can render passes, including the ones only reachable in an error state.

---

### Task 4: The needs-review screen (RF-144)

**Files:** `apps/web/app/laudo/[id]/needs-review.tsx` or equivalent, tests.

An invoice the pipeline could not read honestly says so and offers a better photo. It never shows a partial report assembled from what little was extracted — that is the A8 principle as a screen, and the temptation is real, because a half-read invoice does contain some rows.

§8.1's message is the text: *"Não conseguimos ler essa fatura com segurança. Tente uma foto mais nítida."*

---

### Task 5: The shareable card (RF-145)

**Files:** `apps/web/app/api/card/[invoiceId]/route.tsx`, tests.

`ImageResponse`, 1200×630, carrying no name, CPF, line number or address. RF-145's acceptance asks for two tests: a visual one, and one that **verifies the absence of PII in the card's payload** — not only in the rendered image. Work out the difference and test both.

The card is a public URL. Decide how it is addressed so that possessing an invoice id is not enough to fetch someone's card, and say what you chose.

---

### Task 6: The public report page (RF-146)

**Files:** `apps/web/app/l/[token]/page.tsx`, the token's storage and revocation, tests.

Anonymised data, an upload call to action, a random revocable token. Acceptance: it works with no session, and returns 404 once revoked.

This is the product's first surface reachable with no session at all, so it is the first place a leak is public rather than private. What it serves is built from data already masked in the database, plus a second check before responding — two gates, because there is no session boundary behind it.

Decide what "anonymised" means concretely here beyond `INV-007`'s markers: the issuer's name, the amount and the number of findings are the point of sharing; anything that identifies the person is not.

---

### Task 7: Claiming a session by e-mail (RF-147)

**Files:** `apps/web/app/api/sessions/claim/route.ts`, the confirmation path, `packages/db` migration for the code, tests.

§8.2: `POST /api/sessions/claim` with `{ email }` sends a code; confirming it migrates the anonymous session's invoices to the user, losing no findings.

§8.3 caps this at **3 per hour per e-mail**, and no rate limiting exists anywhere in this codebase yet — this endpoint sends mail on demand to an address the caller supplies, so it is the one that most needs it. Build the limit here even though §8.3's other three limits are out of scope, and say how it behaves under a genuine retry.

The code is a credential: decide its lifetime, how many attempts it allows, and whether it is single-use. Say what you chose and why.

---

### Task 8: The performance and accessibility gates (RNF-03, RNF-05, RNF-09, RNF-10)

**Files:** `.github/workflows/ci.yml`, whatever configuration the tools need, tests.

§18 makes RNF-01 and RNF-03 the block's own definition of done, and E0's final review already recorded that §16.4's Lighthouse and axe steps have no CI job. This block is the first with screens to measure, so it is where they stop being aspirational.

Add: a Lighthouse budget on the pages this block ships (RNF-03's LCP ≤ 2,0 s, RNF-04's CLS ≤ 0,05), the `next build` bundle budget of RNF-05, and axe over the report and public pages with no critical violation (RNF-09). Prove each gate fails when it should — a budget nobody has watched reject a build is a budget that will be discovered to be misconfigured on the day it matters.

**Task 1 is the dependency everything else waits on**, and it is the one with a real design decision rather than a transcription: making the queue asynchronous changes what an HTTP failure means, and the answer must not be that failures become invisible.

**The risk specific to this block** is that it is the first where a defect is a sentence a person reads. The forbidden-term lint exists and is enforced in tests; use it on every string, including the ones only an error path can produce.
